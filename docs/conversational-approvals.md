# 对话批准：干净成片与旧签名包装边界

干净成片现由宿主Agent读取真实直接用户消息，在完整文稿明确获批后自动调用本地干净渲染器；不要求用户终端签名。其可编辑审计笔记不是独立可验证的宿主签名，也不供旧签名包装入口消费。以下“当前缺口”专指保留的签名版HyperFrames包装工具链，不能作为阻止独立干净成片交付的理由。

用户的目标流程始终是：给录音与风格要求，在对话中审核口播稿，再审核导演脚本，随后收下视频。只有两道内容审核；手工终端签名不是这个产品要求的一部分。

## 当前实际行为

| 路径 | 用户操作 | 能证明什么 |
| --- | --- | --- |
| 目标对话流程 | 对当前口播稿明确确认；对当前导演脚本明确确认 | 尚缺可信平台适配器，当前不能宣称生产已支持 |
| 当前生产实现 | 本人首次在终端 setup；每道审核运行 approve、确认摘要、输入口令 | 已配置持钥者批准当前审核包；不证明听感正确 |
| 既有隔离交互测试 | 测试者自然语言回复，控制器记录独立模拟回执 | 两道模拟交互和测试导出；不是 owner 生产批准 |

当前 `review_approval.py` 用用户保管的私钥签发回执，生产验证读取操作系统账号配置中的公钥。请求摘要同时绑定项目、阶段、修订代次、审核文档及源/产物证据。签名保护的是确认来源和版本完整性；可以由可信宿主在用户对话确认时完成，不必要求用户每次运行 CLI。

现有仓库还没有这种宿主适配器。不能用 Agent 写入的 `role=user`、复制的回复、聊天摘要、消息 ID、`approved=true` 或自选公钥替代它。即使文字确实看起来像用户所说，本地验证器也不能仅凭 Agent 可编辑的文件确认来源。模拟测试控制器的签名同样不能提升为 owner 签名。

## 所需的安全接入

可行的调整是由运行 Agent 的可信宿主处理当前两道确认，签发专用内容批准凭证；Agent 只准备请求和消费结果，不持有签发能力。凭证至少需要：

- 宿主验证的真实 owner 身份、会话/消息 ID、直接用户输入来源及明确批准决定；委派消息、Agent 消息、工具输出和测试身份被排除。
- 已展示审核包的精确 request digest、项目、阶段、修订代次和审核文档摘要；先展示，再确认，不能把既往无关的“可以”套在新稿上。
- 宿主明确采集的批准决定。自由文本中含修改条件、含糊回复或模型推断不能自动落为批准；必要时在同一道审核内使用“批准本版／修改”的对话选项。
- Agent 无法伪造的宿主签名/验证端点，可信签发者和 owner 绑定配置位于 Agent 可写工程之外；模型不能提供任意验证公钥或自建签发器。
- 变更失效、撤销/重复消费处理、保留原始确认凭证与审核包；生产、fixture、simulation 三种来源严格分开。

接入后，用户步骤应回到两次对话确认，无须私钥口令或签名 CLI。平台的命令授权、素材上传与费用授权仍各自遵守原权限要求，不能把命令工具的自动审批当作用户内容批准。

更换生产信任来源属于安全敏感改动。当前审计环境提供的对话读取/提问工具没有签发上述凭证的接口，也不能把工具返回内容当作仓库可独立验证的宿主签名。因此本轮未更换验证器、未创建生产身份、未降低两道门禁，也没有把这个方案标为已实现。还需可信宿主的正式确认接口及其 owner/签发者绑定；在此之前，真实纯对话生产闭环仍是明确未填补的使用缺口。

## 验证范围

`tests/test_conversation_boundary.py` 用独立临时测试密钥验证现有门禁：无签名的聊天封套、Agent 自造 owner 字段、模拟回执、错误签发者、旧版本均被拒绝；有效的当前版本签名仍通过。它不是一个真实 owner 对话适配器的成功测试。既有 E2E 的自然语言回复来自隔离模拟测试，不能用来证明上述生产接口已经存在。
